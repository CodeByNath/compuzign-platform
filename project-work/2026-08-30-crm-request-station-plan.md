## Locked CRM-1A direction
Validated `/requests/submit` creates the authoritative durable `cz_request` immediately with lifecycle `pending` and new `CZR` Platform ID. Durable CRM data is the pristine validated business payload. The 7-day `cz_quote_<ref>` transient remains secure quote-view storage only. `quote_ref` stays customer-facing; `CZR` is internal stable identity. No pricing/re-resolution, backfill, or CRM UI in 1A.

Lifecycle: `pending -> approved` or `pending -> cancelled`; same-state repeats are idempotent; opposite terminal transition rejects. Legacy stored `new` normalizes to `pending` on read only.

## Remaining blocker — concurrent ownership / rollback
The revised plan still assumes `RequestRepository::create()` can safely return an existing post while the caller runs reserve/create/assign rollback. It cannot prove that the returned post was inserted by **this** submission.

Current `create()` is lookup-then-insert by `quote_ref`; the meta lookup is not an atomic uniqueness constraint. Two concurrent first submissions can both pass the pre-check. More importantly, if one call receives a post created by the other and identity assignment later fails before/around claim, a rollback rule based only on "platform ID empty or equals my reservation" can delete a shared/winning Request that this call did not create.

### Required correction
Before implementation, define an explicit ownership result for durable creation, e.g. `{post_id, created_by_this_call}` (exact API is Claude's choice). **Only a post proven created by the current call may ever be deleted during rollback.** An existing/concurrently-created post must never be deleted by the losing request.

Also state how same-`quote_ref` concurrent creation is prevented or converged without leaving duplicate `cz_request` posts/CZR identities. Keep the mechanism narrow and Request-specific; do not invent a platform-wide locking framework.

Add regression coverage for two concurrent first submissions of the same `quote_ref`: one durable Request, one CZR, no losing rollback deletes the winner, and conflicting payload still fails closed.
